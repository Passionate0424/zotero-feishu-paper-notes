# Zotero 标注路由

## 颜色语义

| 颜色 | Hex | 用户语义 | 默认处理 |
|-|-|-|-|
| 蓝色 | `#2ea8e5` | 论文关键点 | 进入正文主线，重点解释其因果作用 |
| 黄色 | `#ffd400` | 强调内容 | 同样进入正文主线；按重要性适度突出 |
| 紫色 | `#a28ae5` | 疑问/关键理解 | 回到全文求解，保留问题或理解线索，在相关位置完整呈现 |
| 历史洋红色 | `#e56eee` | 疑问/关键理解 | 与紫色统一处理 |
| 绿色 | `#5fb236` | 论文缺陷 | 放在相关方法、假设或评估附近 |
| 红色 | `#ff6666` | 疑似论文错误 | 独立复核后就地说明 |
| 橙色 | `#f19837` | 可追溯知识 | 补充必要背景或形成延伸线索 |

颜色只表示处理意图，不取代对原文语义的判断。

## 蓝色与黄色：共同组成主线

- 将两类标注与论文地图合并，按论文叙事排序，不按颜色分节。
- 蓝色通常承担关键论点、机制或结论；黄色常承担定义、条件、数据和需要记住的细节，但黄色也可能是主线核心。
- 黄色的强调格式从弱到强选择：正文 → **加粗关键短语** → 表格关键单元格 → 提示块。不要把每条黄色标注都做成提示块。
- 合并相邻或重复标注，保留最完整的上下文和最精确的表述。

## 紫色：先解决，再决定呈现形态

在后台为每个问题记录：原文位置、问题本质、回答、置信边界、正文落点。

- 文字批注优先保留用户原话、术语、例子与理解顺序；只修正笔误、改善句式并补必要前提和推导。在相关小节用一个完整段落或高亮块呈现，避免将一条批注拆散到多个论述中。
- **关键机制理解**：保留问题的核心问法或判断线索，紧邻补出机制解释。可改为简短主题句，无需强制使用或删除“问：/答：”；最终能辨认出用户原本关注的关系。
- **公式或数据流问题**：紧邻公式、流程或图表解释。
- **评估口径问题**：放入实验设置、基线或结果分析。
- **独立批判或重要延伸**：使用旁路批注/提示块。
- **证据不足**：明确保留为存疑点。

只有用户明确要求逐题回答，或问题彼此独立无法自然融合时，才输出单独问题清单。

## 绿色、红色与橙色

- **绿色**：区分作者承认的局限、实验暴露的边界和用户提出的批判；不要笼统写“存在局限”。
- **橙色（#f19837，可追溯知识 / Follow-up）：文献溯源与反观对比三步法**：
  用户标记橙色，意在通过扩展追溯论文所引用的方法或文献内容，根据其真实机理反观论文本身。必须严格执行以下三步闭环，严禁凭空脑补通用套话：

  1. **第 1 步：双重锚定语境与用户意图（Contextual Intent & Citation Grounding）**：
     - **锚定原著上下文论证角色**：仔细研读橙色划线在原文段落中的前后逻辑——查明作者在当前语境下引用该文献究竟扮演什么角色（是作为硬件瓶颈的底层物理证据？是作为被替代的传统基线？还是作为正交互补的系统？），防止脱离上下文盲目检索；
     - **精准锚定用户的批注意图**：结合用户留下的文字批注（例如：“可以追溯一下这篇文章”、“这里给出了延时计算方法供后续实验指导”、“需要有选择性而不是全部存储结果”），明确用户关注的核心命题是“微架构缺陷”、“延迟建模与实验方法”还是“片上 Cache 的工程折中”，确保溯源方向与用户的研究关注点 100% 对齐；
     - **锁定引文与实体**：提取 References 中的完整论文标题、作者团队、发表会议/期刊与年份；针对该特定工作核实其真实学术实体出处，严禁字面拆分专有名词。

  2. **第 2 步：真实检索追溯被引内容（The Former：深入被引机理）**：
     - 仅针对该橙色项调用学术检索工具（如 search_web），深入查明被引文献的核心微架构设计、理论模型、实测证据与底层缺陷；
     - 准确提炼其关键机理（例如：文献 [69] 揭示的 GPU Intra-SM 中 CUDA Core 与 Tensor Core 资源争抢及缺乏弹性 Block 调度；文献 [32] LUT-DLA 揭示的全对全预计算存储爆炸与冷质心冗余）。

  3. **第 3 步：反观论文本身与批判性反思（The Latter：反观对比与局限）**：
     - **反观设计动机**：本篇论文为何做出当前选择？（如 VQVLA 为何因 GPU 缺陷而转向专用双阵列 ASIC；为何放弃全量查表而提出 Top-15% 热点静态 Cache）；
     - **反观工程折中与局限**：结合用户文字批注（如“离线确定 Tag centroidID 免除 LRU 设计”），批判性分析其工程代价、长尾突发扰动下的泛化脆弱性（OOD 场景失效）以及硬件分裂开销；
     - **概括浓缩整合**：所有橙色线索概括提炼为逻辑闭环的专题条目，统一收敛至独立的“第四章：待深入与可追溯线索”，严禁碎片化散落。

## 旁路高亮块 vs 融入正文：交互决策协议（ask_question）

在进入成文或制定计划时，严禁 AI 擅自替用户裁决关键深度批注的版面形态。针对具有呈现双重性（既可作为正文逻辑段落，又可作为独立高亮块/提示块）的高价值点，必须调用 `ask_question` 工具向用户征询呈现偏好。

### 1. 触发场景与候选点筛选（防过度打扰）

为保证阅读流连贯且避免提问疲劳，**单篇论文通常聚焦 1~4 个争议焦点集中提问**，严禁对每条普通标注都提问：

| 触发场景 | 典型特征 | 裁决核心（为什么需要提问） |
| :--- | :--- | :--- |
| **复合型紫色批注** | 批注包含“前提 → 机制 → 例子/反例 → 取舍”多层逻辑 | 作为小节自然段，还是保留为醒目的【💡 关键理解】高亮块？ |
| **架构取舍与批判性反思** | 批注涉及跨领域对比（如对标其他论文/同类 ASIC 缺陷） | 融入当前硬件模块正文，还是作为独立的旁路对比高亮块？ |
| **疑似错误 / 存疑推导（红色）** | 发现符号丢失、位宽溢出或公式存疑，但论文未开源验证 | 就地给出条件限定正文，还是作为独立的【🔍 存疑】提示块？ |
| **高价值延伸线索（橙色）** | 既影响当前小节的硬件动机，又是可追溯的独立工作 | 放在正文作为动机铺垫，还是收敛进【第四章：待深入与可追溯线索】？ |

> **常规免问规则**：纯蓝色主线事实、单一黄色加粗、定义说明、纯图表引述等，一律遵循默认规则直接融入正文，无需提问。

### 2. ask_question 调用规范

调用 `ask_question` 时必须严格遵守以下格式要求：

- **题干（question）结构**：必须包含 `[页码/小节定位]` + `[用户原始批注摘要]` + `[呈现争议焦点]`；
- **选项（options）结构**：
  - 第 1 个选项必须是 `(Recommended) [推荐选项]：[专业推荐理由]`；
  - 提供 2~3 个具体、互斥的排版走向选项（如：融入正文自然段落、独立【💡 关键理解】高亮块、独立【🔍 存疑】提示块、收敛入第四章专题）；
  - `is_multi_select` 设为 `false`。

### 3. 决策闭环与落地

用户完成选择后：
1. **固化记录**：后台在审计映射表中登记为：`annotation_key -> user_selected_format`；
2. **大纲体现**：在笔记大纲与计划输出中，明确标注该点采用的版面形式（如标注 `[高亮块-关键理解]` 或 `[正文自然段]`）；
3. **XML 精确兑现**：在生成飞书 XML 时，严格使用 `<callout>` 或 `<p>`，杜绝后续擅自篡改。

## 交接到最终审计

完成颜色路由后，使用 [annotation-audit.md](annotation-audit.md) 对每条标注做最终覆盖检查。该审计负责判定正文落点、关键理解是否直接阐述、问题是否得到回答，以及重复标注是否可以合并；不要在此处重复维护另一份覆盖清单。
