# 内容核验与推导

## 写作原则

把核验放在后台完成。最终笔记直接、自然地解释论文，避免反复写“论文原文指出”“有直接证据”“根据表格可知”。只在自行计算、推断前提、纠错、指标口径或真实未知会影响理解时，就地简短说明一次。作者明确的局限集中呈现；未展开的实现细节放待深入线索，不给每段加边界或免责声明。保留必要限定，但不把“严谨”写成反复纠偏。

语言审校后重新核验技术内容，避免把简洁误做成过度断言；语言审校的具体规则见 `writing-style.md`。

## 后台核验顺序

1. 读取原文段落及其前后文。
2. 核对关联公式、图、表、脚注和附录。
3. 必要时核对作者代码、补充材料或正式勘误。
4. 硬件、协议和器件事实优先核对官方手册或标准。
5. 仍不足时再查可靠二手资料，并避免把二手解释写成论文主张。

## 事实与推导

- 不把参数符号擅自替换为具体数值；论文只写位宽 `B` 时，不默认 `B=8`。
- 不把不同指标相互替代，例如 bit sparsity 不等于 element sparsity。
- 不把相关性、相似度或消融结果写成论文未证明的因果关系。
- 自行计算时写清输入数据、公式、单位、舍入方式和适用条件。
- 从图中估读数值时使用“约”，并避免制造超过图像分辨率的精度。
- 推断成立依赖额外假设时，把假设与结论写在同一处。
- 论文和公开材料都未说明时，直接写“论文未说明”或“现有材料无法确认”。

## 公式与实现

- 逐项检查符号、上下标、维度和单位。
- 区分数学恒等式、论文近似、硬件化简和实现启发式。
- 化简涉及平方、绝对值、量化、截断或符号位时检查信息是否丢失。
- 区分算法并行、硬件流水、batch 并行和时间上的重叠；不要只用“并行执行”一笔带过。
- 区分论文宣称的实现与根据架构图推测的实现。

## 疑似错误与缺陷

处理红色标注时：

1. 原样还原论文公式、图注或数据口径。
2. 给出最短可复核的反例、维度检查或数值推导。
3. 检查是否存在版本差异、排版错误或术语歧义。
4. 结论成立后，说明错误会影响公式、实现还是仅影响文字表述。
5. 若无法定论，将其写成存疑，不写成确定错误。

处理绿色标注时，说明缺陷对应的前提、基线、数据集、硬件条件或泛化范围，避免抽象批评。

## 外部检索

需要联网时优先级如下：

1. 论文正式版、附录、作者仓库、勘误。
2. 官方标准、芯片/框架手册和 API 文档。
3. 被论文明确引用的原始研究。
4. 可靠二手技术资料，仅用于辅助理解。

最终正文只保留对理解有用的结论和必要链接，不写检索流水账。
